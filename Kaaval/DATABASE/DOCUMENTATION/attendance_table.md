# KAAVAL – Attendance Table Design

## 1. Table Name

`attendance`

## 2. Purpose

The attendance table stores student check-in records generated by KAAVAL fingerprint attendance devices.

## 3. Table Columns

| Column Name | Data Type | Constraint | Purpose |
|---|---|---|---|
| attendance_id | BIGINT | PRIMARY KEY, IDENTITY | Unique attendance record ID |
| student_id | BIGINT | FOREIGN KEY, NOT NULL | Student reference |
| device_id | BIGINT | FOREIGN KEY, NOT NULL | Device reference |
| attendance_date | DATE | NOT NULL | School attendance date |
| check_in_time | TIMESTAMPTZ | NOT NULL | Actual check-in timestamp |
| status | VARCHAR(20) | NOT NULL | PRESENT or LATE |
| event_id | UUID | UNIQUE, NOT NULL | Unique attendance event ID |
| created_at | TIMESTAMPTZ | DEFAULT CURRENT_TIMESTAMP | Record creation time |

## 4. Column Details

### 4.1 attendance_id
- Unique ID for each attendance record.
- Primary Key.
- Automatically generated.

### 4.2 student_id
- Identifies the student.
- Foreign Key referencing students.student_id.
- Cannot be NULL.

### 4.3 device_id
- Identifies the KAAVAL device that submitted the event.
- Foreign Key referencing devices.device_id.
- Cannot be NULL.

### 4.4 attendance_date
- Stores the school attendance date.
- Uses DATE format.
- Must follow the school's Asia/Kolkata attendance date rules.

### 4.5 check_in_time
- Stores the exact check-in timestamp.
- Uses TIMESTAMPTZ.
- Cannot be NULL.

### 4.6 status
- Stores the attendance status.
- Initial allowed values: PRESENT and LATE.
- Cannot be NULL.
- Status must be calculated using the school's approved attendance rules.

### 4.7 event_id
- Stores a unique identifier for each attendance event.
- Uses UUID.
- Must be unique.
- Supports safe offline synchronization and duplicate event detection.

### 4.8 created_at
- Records when the database record was created.
- Default value is CURRENT_TIMESTAMP.

## 5. Constraints and Duplicate Prevention

- attendance_id must be unique.
- student_id must reference an existing student.
- device_id must reference an existing device.
- event_id must be unique.
- Only one accepted check-in per student per attendance_date is allowed in this initial design.
- Use UNIQUE(student_id, attendance_date) for this rule.
- Duplicate offline events must not create duplicate attendance records.

## 6. Relationships

- students.student_id connects to attendance.student_id.
- devices.device_id connects to attendance.device_id.
- One student can have multiple attendance records across different school days.
- One device can submit multiple attendance records.

## 7. Attendance Processing Rules

1. Fingerprint sensor identifies the enrolled fingerprint slot.
2. The ESP32 maps the fingerprint slot to the registered student.
3. A unique attendance event is created.
4. The server validates the student and device.
5. The server checks for duplicate events and existing daily attendance.
6. The server calculates the attendance status using approved school rules.
7. The server stores the accepted record.
8. The device marks the event as synchronized only after server acknowledgement.

## 8. Time and Date Rules

- Use Asia/Kolkata for school attendance date calculations.
- Store timestamps with time-zone awareness.
- Do not trust an unverified device clock for final attendance decisions.
- Define school working days and holidays separately.

## 9. Security Rules

- Only authenticated and active devices can submit attendance.
- Only valid and active students can receive attendance records.
- Teachers can view only authorized student records.
- Parents can view only their linked children's attendance.
- Attendance history must not be publicly accessible.
- Use dummy student records during development.
